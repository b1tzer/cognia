# 通用需求交付流程 SOP（元流程）

> 本文件是**适用于所有需求的最基础交付流程**，与具体项目、技术栈、团队分工无关。
> 任何需求——功能开发、bug 修复、文档编写、调研、数据制作等——都遵循下面的「四阶段闭环」：
>
> **调研 → 设计 → 开发 → 验收**
>
> 它回答一个根本问题：**一个需求，从提出到被确认「做完」，到底要走哪几步、每一步做到什么程度才算合格。**

---

## 阶段一：调研（先看行业怎么做）

**目的**：避免闭门造车，站在成熟方案的肩膀上设计，而非凭直觉拍脑袋。

**怎么做**：

1. 明确这个需求要解决的**核心问题**是什么。
2. 用搜索引擎多方交叉验证，看**行业优秀案例、优秀产品、开源优秀实现**是怎么做的：
   - 竞品是怎么处理同样问题的？
   - 有没有公认的最佳实践 / 设计模式 / 标准？
   - 别人踩过什么坑、有哪些反例？
3. 至少看** 2-3 个不同来源**，交叉印证，不要只看第一篇就下结论。

**产出物**：一份「调研结论」——列出的**关键最佳实践清单**（每条标注来源依据），作为下一阶段设计的输入。

**阶段完成标准**：
- 核心问题的行业解法已搞清楚，有 2-3 个来源支撑
- 能说清「别人为什么这样做、我们该借鉴什么、该避免什么」

---

## 阶段二：设计（看现状 → 定方案 → 定需求用例 → 定验收标准）

**目的**：把模糊的「想要」翻译成**有标准、可验收、可测试**的「做什么、做到什么程度」。

**怎么做**（按顺序）：

1. **看现状**：先摸清当前项目的结构、已有代码/资源，搞清楚「在这个基础上，最佳落点在哪」。
2. **定方案**：结合阶段一的调研结论 + 现状，选定**最佳设计方案**（在备选方案中说明取舍理由）。取舍依据用**优先级框架**量化，而非「谁嗓门大」：
   - **MoSCoW**：Must / Should / Could / Won't，强制明确「这次不做」哪些；
   - **RICE**：Reach × Impact × Confidence ÷ Effort，量化打分排序；
   - **Kano 模型**：区分基本型 / 期望型 / 兴奋型，别在基本体验缺失时堆「炫技」功能；
   - **价值 vs 复杂度四象限**：优先做「高价值、低复杂度」。
3. **定需求用例**：明确「我们到底要把它做成什么样」——即**具体的、可观测的行为/产出**，而不是抽象愿望。用例（用户故事）用 **INVEST 原则**检验质量：**I**ndependent 独立、**N**egotiable 可协商、**V**aluable 有价值、**E**stimable 可估算、**S**mall 足够小（一次迭代内能完成）、**T**estable 可测试。
4. **定验收标准**：给需求用例逐条配上**可测试的验收条件**。

**验收标准的两种形式**（行业通用，二选一或结合）：

- **AC（Acceptance Criteria，验收标准）**：针对**这一个需求**的具体可测条件。写作原则：**What 而非 How**（描述结果，不描述实现）、**可量化、可测试**、覆盖**正常路径 + 边界/异常**。推荐「Given-When-Then」格式或规则清单。
- **DoD（Definition of Done，完成定义）**：适用于**所有需求**的通用质量门槛（如：代码有测试、通过 code review、无新增 lint 错误、文档已更新等）。

**两扇配套闸门**：

- **DoR（Definition of Ready，就绪定义）**：需求进入开发前必须「足够清晰」——角色/目标/价值明确、验收标准已就位、依赖已识别，否则不准开工。
- **Out of Scope（不做清单）**：每个需求必须**显式列出「这次不做什么」**，防止范围蔓延（Scope Creep）与「顺手多做无关项」。

**产出物**：设计方案（含取舍理由与优先级依据）+ 需求用例清单（通过 INVEST 检验）+ 不做清单（Out of Scope）+ 验收标准（AC + DoD + DoR）。

**阶段完成标准**：
- 需求用例足够具体，任何执行者读完都清楚「要做出什么」，并通过 **INVEST 检验**（尤其是「足够小、可测试」）
- 每条验收标准都**可测试、可量化**（避免「体验流畅」「加载快」这类无法验证的模糊描述）
- 覆盖了正常路径 + 关键边界/异常情况
- 已显式列出**「这次不做什么」（Out of Scope）**

## 阶段三：开发（含强制自测）

**目的**：把设计落地成可验收的成果；**未经自测的成果不得声明「已完成」**。

**怎么做**（标准开发流程）：

1. **版本控制 + 分支**：从主分支切独立分支开发，用 `git commit` 做**小步提交**（每完成一个可独立验证的小块就提交一次，作为过程锚点）。
2. **小步实现**：优先采用「先写测试再写实现」的 TDD 节奏（Red 写失败测试 → Green 最小实现 → Refactor 保持测试绿），至少做到「每改一处配一处测试」。
3. **强制自测环节**（完成前必须全部通过，缺一不可）：
   - 新增/修改的功能有对应**单元测试**，且通过
   - 跑**全量回归**，确认没有破坏已有功能
   - 静态检查（lint/类型检查等）无新增告警
   - 手动验证**正常路径 + 边界 + 异常**三种情况
4. **自查清单**（声明「做完」前逐条勾选）：
   - [ ] 需求用例全部实现，无遗漏
   - [ ] 自测全部通过（单测 + 全量回归 + lint）
   - [ ] 边界/异常情况已处理并验证
   - [ ] 没有引入与需求无关的改动

**产出物**：可验收的成果 + 自测结果记录（测试通过情况、覆盖了什么）。

**阶段完成标准**：
- **自测全部通过后才能声明「已完成」**（这是硬门槛，不允许跳过）
- 成果与需求用例、验收标准一一对应，无遗漏

---

## 阶段四：PM 验收

**目的**：以产品经理视角，确认成果**真的合格**，而非仅「能跑通」。

**怎么做**（三大维度，逐一核查）：

1. **完整性**：对照阶段二的**需求用例 + 验收标准**，逐条核对，确认**每一个需求都已实现且没有遗漏**；同时确认没有多做无关的东西。
2. **逻辑合理性**：产品的**使用逻辑是否符合行业惯例**——交互流程、信息架构、边界处理是否符合用户对同类产品的既有认知，有没有反直觉的地方。
3. **显示效果**：实际看一遍**显示效果有没有明显问题**——布局错乱、样式丢失、状态展示错误、异常态/空态缺失等肉眼可见的缺陷。

**产出物**：验收结论——「通过」或「打回（附具体问题清单）」。

**阶段完成标准**：
- 三个维度都核查通过，才可判定需求「完成」
- 打回时给出**具体的、可执行的问题清单**（而非「感觉不对」），让执行者知道改什么

---

## 贯穿全程的两条硬规则

1. **没有验收标准，就不算设计完成**；没有自测通过，就不算开发完成；没有三大维度核查，就不算验收完成。
2. **每一阶段都有明确的「完成标准」**，上一阶段不达标，不允许进入下一阶段——用「门禁」保证质量，而非靠事后补救。

## 元流程的自我进化（Meta-SOP）

本 SOP 本身也不是一成不变的，它通过下面这个闭环持续迭代：

```
查 SOP  →  执行  →  AAR  →  反哺优化/新建 SOP
   ↑                              │
   └──────────────────────────────┘
```

1. **操作前**：先查看 SOP（本文件 + 项目特定 SOP），确保按既定标准流程执行，不凭记忆即兴发挥。
2. **执行**：按四阶段闭环（调研 → 设计 → 开发 → 验收）完成操作。
3. **操作后（AAR）**：做一次 AAR 复盘，评估本次执行中——
   - 是否暴露了某条 SOP 的**缺陷或不足**（应更新已有条目）；
   - 是否沉淀了**可复用的新经验**（应新建一条 SOP）。
4. **反哺**：把 AAR 结论落回文档，让流程规范随实践持续进化。

这样，SOP 不再是一次性写死的文档，而是一个**自我学习的活体规范**——每做完一件事，流程本身都会变得更准、更稳。
