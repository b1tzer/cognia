# Cognia 需求规格（Spec）

> 本文档描述 Cognia「是什么、为什么、怎么算完成」，刻意不涉及技术实现（技术方案见 plan 阶段）。

## 1. 背景与目标

- 产品：AI 主动学习教练（见 product-brief.md）
- 核心差异化：不是用户发现自己不懂后再问 AI，而是 AI 主动发现用户哪里没懂
- 初始用户：程序员，学习新框架 / 编程语言
- 核心假设：AI 能通过用户的「表达」持续判断其真实认知状态，并据此主动调整学习过程
- 本规格只描述「是什么、为什么、怎么算完成」，不涉及技术实现

## 2. 核心概念定义（领域词汇表）

- **知识模型（Knowledge Model）**：
  针对一个学习目标，AI 生成的结构化知识点集合 + 依赖关系。每个知识点有唯一 ID、名称、描述、前置依赖。
  例：目标「React Hooks」→ 知识点包含 useState / useEffect / 依赖数组 / 闭包陷阱 / useRef 等，依赖关系：useEffect 依赖闭包；依赖数组依赖 useEffect。

- **认知状态（Cognitive State）**：
  用户对某个知识点的真实掌握情况，是 Cognia 的核心诊断对象，取值为四态之一：
  ① mastered（已掌握）：能正确解释并正确应用
  ② partial（部分掌握）：能说大意，但细节模糊或说不清边界
  ③ misconception（错误理解）：理解有偏差，但用户自认为是对的 ← 最有价值的诊断对象
  ④ unknown（盲区）：用户完全不知道这个知识点存在 ← 最有价值的诊断对象

- **盲区（Blind Spot）**：= unknown 状态。用户「不知道自己不知道」的知识点。

- **错误理解（Misconception）**：= misconception 状态。用户「以为自己懂了但实际错了」的知识点。

- **表达（Articulation）**：
  用户用自己的话解释知识点、或回答问题。这是 AI 诊断的「唯一输入来源」。关键约束：诊断只能基于用户如何表达，不能基于用户是否点击「我懂了」按钮。

- **知识熟练度 JSON（Proficiency JSON）**：
  每个用户对每个知识点的认知状态的结构化记录，随学习动态变化，必须增量 Delta 更新（见 constitution §5）。

- **主动干预（Proactive Intervention）**：
  AI 在诊断出盲区 / 错误理解后主动发起的教学动作，含四类：
  - 追问：用探针提问暴露盲区
  - 解释：补盲区
  - 纠错：修误解
  - 回溯：返回前置知识点
  **干预类型与认知状态对应关系**：partial 采用「引导型干预」（渐进式补全、追问澄清）；misconception 采用「颠覆型干预」（先指出认知冲突、重建正确模型，而非简单补充）。

## 3. 范围边界

### MVP 包含（In）

- 学习目标设定（用户提出要学什么）
- 知识模型构建（AI 拆解知识点 + 依赖关系）
- 对话式表达与诊断（用户表达 → AI 判断认知状态）
- 主动干预（追问 / 解释 / 纠错 / 回溯）
- 认知状态追踪（知识熟练度 JSON 的增量更新）

### MVP 明确排除（Out）

- 登录 / 注册 / 完整账号体系（属「价值层」，北极星验证前不做）
- 付费 / 权限 / 角色体系
- 多学科通用支持（只做「编程框架 / 语言」这一类知识域）
- 课程内容库 / 课件制作（AI 基于 LLM 知识即时生成，不做预置内容库）
- 社交 / 协作 / 排行榜
- 移动端 / 多端

### 多租户隔离的 MVP 平替方案

> 虽然账号体系（登录 / 注册）MVP 排除，但为遵守宪法 §5 的多租户隔离原则，底层数据契约**保留 user_id 字段**。MVP 阶段由前端在运行时随机生成一个 `mock_user_id`（如 `user_guest_123`），通过 Runtime Context 注入（不塞进 State）。这样在无登录的情况下依然实现「每人一套独立记忆」，后续可无缝升级到 Supabase Auth，仅替换 user_id 的来源，不改动数据层与编排层。

## 4. 黄金路径（用户故事 + 验收标准）

### US-1 设定学习目标

- 用户：我要学 React Hooks
- 系统：确认学习目标，生成该目标的知识模型（知识点 + 依赖关系），并展示给用户
- 验收：
  - 知识模型包含合理数量的知识点（5~15 个），且依赖关系正确
  - **前置约束**：若用户输入的学习目标过大（如「学 Python」），AI 必须先主动引导用户缩小到原子目标（如「学 Python 装饰器」），再生成知识模型，禁止直接对过大的目标拆解

### US-2 用户表达理解

- 用户：用自己的话解释某个知识点，或回答 AI 提出的问题
- 系统：记录用户表达内容
- 验收：表达内容被结构化保存，可供后续诊断引用

### US-3 诊断认知状态

- 系统：基于用户表达，对相关知识点给出四态诊断 + 置信度 + 证据（用户原话）
- 验收：诊断结果结构化输出，每个知识点都有明确状态 + 可追溯的证据片段

### US-4 主动干预

- 系统：针对盲区 / 错误理解，主动发起追问 / 解释 / 纠错 / 回溯
- 验收：AI 的干预动作能对应到「哪个知识点、哪种状态、什么干预类型」；干预类型与认知状态匹配（partial → 引导型、misconception → 颠覆型）

### US-5 持续验证直至掌握

- 系统：重复 US-2~US-4，直到某知识点达到 mastered，或用户主动结束
- 验收：学习过程有明确的「掌握判定」和「结束条件」，不会无限循环

### US-6 认知状态回写

- 系统：将诊断结果增量写回该用户的知识熟练度 JSON（不覆盖历史）
- 验收：熟练度 JSON 保持增量更新，历史状态可追溯

## 5. 数据契约雏形

- **知识模型（Knowledge Model）**
  结构：学习目标 + 知识点列表 + 知识点间依赖关系

- **认知诊断结果（Diagnosis）**
  结构：知识点 ID + 认知状态（四态）+ 置信度 + 证据（用户原话片段）

- **知识熟练度 JSON（Proficiency JSON）**
  结构：user_id + 学习目标 + 知识点 ID → 认知状态（含时间戳 + 更新类型 Delta）
  注意：这是「长期记忆」的一部分，遵守 constitution §5 的增量更新与隔离规则。user_id 字段在 MVP 阶段为 mock_user_id，后续无缝升级为 Supabase Auth 的真实 user_id。

## 6. 边界情况与错误条件

- 用户表达太模糊，AI 无法诊断 → 应主动追问澄清，而非瞎猜状态
- 用户中途换学习目标 → 旧目标的知识熟练度应保留，不被覆盖
- 用户声称「懂了」但表达暴露矛盾 → 以表达为准，不采信自我宣称
- 知识模型超出 LLM 能力（如过新的框架）→ 明确告知「暂不支持」，不硬编
- 学习会话无限延长 → 有明确的结束条件（见 US-5）
- **诊断证据硬性约束**：诊断证据必须来自用户原话，严禁 AI 自行脑补或无端猜测用户的误解；用户未提及的知识点一律归为 unknown
- **干预循环硬性约束**：单知识点的干预流在连续失败 3 轮后，必须触发回溯（返回前置知识点）或挂起（暂停并寻求人工/用户确认），禁止无限循环

## 7. 验收标准（对齐北极星）

- 10 个目标用户，在 1 个标准知识域完成「表达 → 诊断」闭环后：
  ① ≥70% 的 AI 主动指出的盲区 / 错误理解，被用户本人承认
  ② ≥50% 的 AI 诊断，与专家预先标注的缺陷命中
- 诊断结果可被自动打分（结构化输出 + 证据可追溯），支撑 eval harness
